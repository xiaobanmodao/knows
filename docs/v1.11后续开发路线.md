# 知识通 v1.11 后续开发路线

> 路线状态：规格已确认，实施从 `codex/roadmap-v1.11` 开始
>
> 当前运行版本：`1.10.1-dev.1`
>
> 发布分支：`codex/release-regression-v1.10.1`

## 1. 目标与边界

v1.11 的目标是把五科学科内容维护变成可重复、可核对、可回归的开发流程，重点解决教材来源映射、内容复核和发布前差异控制。v1.11 不以新增页面或增加学习任务为目标。

产品继续保持纯知识查阅：不加入在线测评、自动评分、学完自测、单元输出任务、错题本、打卡、家长端、强制登录、云同步或未经人工审核的 AI 讲解。

本路线不改变现有稳定 ID、云资源路径、本地存储版本或备案信息。教材照片、自有教辅和公开资料只用于核对课程边界与知识关系，正文、例句、示例、解析和插图继续原创整理。

## 2. 当前规格确认

### 2.2 运行与发布规格

- 主包、数学、英语、物理、化学和生物继续按普通分包运行，公共组件和轻量搜索索引留在主包。
- 内容仓库继续使用静态 JavaScript，构建期生成搜索索引、审计报告和资源清单。
- 本地记录继续使用 `subjectId:type:id`，不因路线文档升级存储版本。
- 云图片失败时必须保留完整文字内容；未准备好云环境时不得调用无效云接口。
- 运行时版本在 v1.10.1 发布闭环前保持 `1.10.1-dev.1`；不在路线分支提前伪造 `1.11.0` RC。

## 3. 阶段 0：完成 v1.10.1 发布闭环

阶段 0 是 v1.11 继续开发前的发布前置，但发布分支和路线分支必须隔离。

### 3.1 外部状态确认

在微信开发者工具中完成以下操作：

1. 确认当前登录账号拥有 `project.config.json` 中 AppID 的开发权限。
2. 关闭并重新打开当前项目，确认项目绑定的 AppID 与配置一致。
3. 运行预览/上传前置流程，保留完整日志，不把“Using AppID”作为成功证据。
4. 如仍出现 `41002 appid missing`，先处理账号、项目绑定或开发者工具状态，不修改业务代码绕过服务端校验。

发布诊断可在不改动项目的情况下运行：

```bash
cd /Users/hht/Desktop/knows/.worktrees/roadmap-v1.11
node scripts/check-release-tool-state.js --project /Users/hht/Desktop/knows/.worktrees/release-regression-v1.10.1
```

该命令读取项目配置、开发者工具 `islogin` 输出和最近一次 `preview.log`，写入 `tool-state.json`。只有同时出现有效 AppID、已登录和无上传错误时才显示 `ready`；`41002` 会明确记录为 `appid-permission-or-project-binding`，不能替代包体报告或实体设备证据。

路线分支需要汇总独立发布工作树的状态时，使用 `node scripts/check-roadmap-status.js --release-project /Users/hht/Desktop/knows/.worktrees/release-regression-v1.10.1`。该参数只读取发布工作树中的状态报告，不复制或修改发布产物；显式 `--tool-state` 或 `RELEASE_TOOL_STATE` 优先级更高。

报告中的 `blocker.nextActions` 是机器可读的操作清单：

- `cli-login-required`：先登录开发者工具，再重新生成状态报告；
- `appid-permission-or-project-binding`：核对账号开发权限、重新打开项目并重新生成状态报告；
- `preview-upload-failed`：保留完整日志和 request id，排查错误码后再重试；
- `invalid-project-config`：先修正 `project.config.json` 的正式 AppID。

状态没有恢复为 `ready` 前，不重复运行预览上传，也不把“Using AppID”或空的 `packages-preview.json` 当作包体证据。

## 4. 阶段 1：v1.11 来源地图与内容维护

### 4.1 数学新版目录映射

数学新版教材的处理顺序固定为：官方目录证据收集 -> 结构差异报告 -> 稳定 ID 映射 -> 页面显示核对 -> 回归检查。

已公开确认的结构变化可以记录为映射；未取得逐册官方目录时，必须保留 `needs-official-volume-map` 边界。不得因为目录顺序变化而：

- 直接用章节序号重建主键；
- 批量重命名 `ch*`、专题、知识点或模板稳定 ID；
- 删除现有章节或将历史内容强行归入猜测的新版章节；
- 用搜索结果、培训机构目录或单张教材照片替代官方逐册证据。

每个完成的映射至少记录：稳定 ID、教材版本、册次、显示标题、官方小节、来源 URL/PDF、核对日期、变更原因和是否影响旧别名。

### 4.2 英语教材映射

英语五册现有单元和详细词法/语法内容继续保持可查阅。

英语目录门禁已加强为独立官方目录证据：四册具有完整当期目录页证据，九年级上册当前页面只核对 Unit 1-2，其余既有 Unit 3-8 等待完整官方目录复核；该记录只验证目录元数据，不是外部内容来源接入，不解除全局外部资料阻断。真实外部内容来源接入的下一批阻断仍为 `math-chapters-v1.11`，它要求完整官方逐册目录。

人教社公开介绍已确认九年级下册有 5 个正式学习单元和 2 个选学戏剧；本轮再核对人教社官方数字配套资源入口后，仍未取得九下具体标题。只有在正式目录、单元标题和可靠教材文件完成交叉核对后才扩充。此前只记录结构待核对项，不创建空单元、不编造单元标题、不把能力专题伪装成教材单元。

已有词条和语法点的维护必须保留英式主拼写、美式变体、IPA、词性、可数性/及物性、搭配、原创例句、辨析和复核来源字段。

### 4.3 物理、化学和生物维护

按小批次复核以下高风险字段：

- 物理：符号、单位、方向、公式条件、实验步骤、误差、安全提醒和图示连线；
- 化学：化学式、反应条件、配平、实验现象、结论和图片文字降级；
- 生物：术语、观察对象、实验步骤、结论、单元父级和窄屏文字布局。
- 生物来源已补齐教育部课程标准和人教社七至八年级新教材介绍两条稳定 `sourceRefs`，后续新增生物批次继续沿用同一格式。

物理现有 6 个专题已登记 `official-framework-support` 的构建期官方框架佐证，由教育部课程标准和人教社公开新教材介绍支持宏观领域相容性；该记录不验证教材逐章标题、章节顺序、册次映射、正文或原始插图。它是补充性框架佐证，不是 `external-source` 批次，不改变 23 批真实外部资料接入状态、`content-source-follow-up` 的 `blocked` 状态或 `math-chapters-v1.11` 等待完整当期官方逐册目录的阻塞边界。

化学现有 10 个专题也已登记 `official-framework-support` 的构建期官方框架佐证，由教育部化学课程标准、2024 年国家课程教学用书目录和人教社新教材培训公开记录共同提供课程与版本语境观察；该记录只支持现有原创专题的宏观领域相容性和内部快照可追溯，不验证教材逐章标题、章节顺序、册次映射、正文或原始插图。它同样不是 `external-source` 批次，不改变内容源跟进报告的 `blocked` 状态，也不解除数学逐册目录的官方证据门禁。

生物现有 6 个专题也已登记 `official-framework-support` 的构建期官方框架佐证，由教育部生物学课程标准和人教社七至八年级新教材介绍提供课程框架与宏观单元语境。它仅作为补充性佐证，支持现有原创专题与公开框架的宏观领域相容和内部快照可追溯；不验证教材逐章标题、章节顺序、册次映射、正文或原始插图，不是 `external-source` 外部资料输入，不改变 `content-source-follow-up: blocked`，也不解除 AppID、包体或 iPhone/Android 实体设备证据等发布阻断。

每次只处理一个明确批次，完成后立即生成差异报告和检查结果。内容准确性问题与页面交互问题分开提交，避免难以定位回归来源。

## 5. 阶段 2：内容生产与审计底座

在阶段 1 的来源地图稳定后，再逐步建设：

1. 结构化内容输入格式，支持稳定 ID、父级、别名、来源和复核状态；
2. 构建期 schema 校验、搜索索引生成、图片资源检查和差异报告；
3. 人工复核队列，区分待核对、已核对和已发布状态；

当使用 `--require-external-source` 时，批次工具会先写出报告，再以非零退出码阻断非 `external-source` 批次；报告中的 `requirements.externalSourceIssues` 会列出批次 ID、输入路径、实际 `sourceKind` 和阻断原因。使用 `--require-reviewed` 时，报告还会检查每个已读入批次的 `review.untracked`，并在 `requirements.reviewIssues` 中列出未人工复核的实体。这样可以直接把报告交给下一轮资料接入，不需要从终端异常中手工恢复缺口。

资料接入前可先生成执行顺序报告：`node scripts/build-content-source-follow-up.js dist/content-audit/content-source-input-batches/manifest.json --report dist/content-audit/content-source-follow-up.json`。报告按“修复输入 -> 补齐复核状态 -> 接入外部来源 -> 复核差异 -> 补齐文件”排序；同等处理动作下优先展示已有输入文件的批次，`summary.nextBatchId` 给出当前最先处理的批次。每个批次同时输出 `sourceRequirements`，列明官方来源候选、必须保留的证据字段和禁止动作；路线状态命令会把下一批次的证据说明带入下一步提示。报告同时保存 manifest、当前源和批次输入哈希，避免资料更新后误用旧报告。生成后运行 `node scripts/check-content-source-follow-up.js <manifest.json> <report.json>` 重建并比对报告；`--require-ready` 仅在全部批次具备外部来源、没有 `untracked` 且没有其他待处理项时作为阻断门禁。

路线状态命令会同时显示内容源总门禁、当前源状态和外部资料状态。当前源全部通过内部结构/复核审计时显示 `当前源：ready`；没有逐批外部来源凭证时显示 `外部资料：blocked`，总状态仍保持 `blocked`，不会把当前源误报为内容损坏，也不会放宽真实资料接入门禁。

为减少资料接入时的人工整理，`node scripts/build-content-source-intake-pack.js dist/content-audit/content-source-follow-up.json --report dist/content-audit/content-source-intake-pack.json` 会把全部批次的稳定 ID、当前状态、优先级、官方来源候选、必填证据字段、当前差异和预期统计导出为接入包；随后运行 `node scripts/build-content-source-intake-guide.js dist/content-audit/content-source-follow-up.json --output dist/content-audit/content-source-intake-guide.md`，生成按 `summary.nextBatchId` 置顶的人工核对清单，明确每批的来源、字段、禁止动作和提交流程。接入包中的 `sourceEvidenceTemplate` 和清单中的命令只提供空占位与执行顺序，不是外部来源凭证，也不能替代 manifest 审计；取得真实官方资料后，仍须使用 `build-content-source-external-manifest.js` 生成带输入哈希和来源凭证的 manifest。质量矩阵会先重建当前源 manifest 和跟进报告，再校验并生成接入包与清单，避免使用旧的 `dist` 产物。

取得真实外部 manifest 后，可按需运行 `node scripts/check-content-source-url-access.js <manifest.json> --report dist/content-audit/content-source-url-access.json --require-accessible` 检查来源链接是否可访问，并记录 HTTP 状态和最终跳转地址。该检查不进入默认构建矩阵，避免网络波动影响本地确定性构建；默认矩阵只验证其报告契约和无来源/严格模式行为。

若已生成 URL 报告，可通过 `node scripts/check-roadmap-status.js --url-access-report <report.json> --url-access-manifest <manifest.json>` 将失败链接和报告过期状态纳入路线汇总；报告的 manifest 哈希与当前输入不一致时会提示重新生成。未提供 URL 报告时，路线状态显示为 `not-run`，不把尚未执行的按需检查误报为失败。

在尚未取得外部批次输入时，可运行 `node scripts/check-content-source-registry-url-access.js --report dist/content-audit/content-source-registry-url-access.json` 检查注册表中全部官方/参考来源 URL。该命令按 URL 去重并保留来源键、规范入口/备用入口角色、最终地址和 HTTP 状态；同一来源只要有一个官方入口可访问，来源解析状态即为 `passed`，但规范入口的失败仍会保留在报告中。它是来源基础设施诊断，不会把 `current-fixture` 转为 `external-source`，也不会解除真实内容来源门禁，不能用网络诊断结果替代逐批教材证据。
